🚩 READY FLAG SYSTEM (logs/ready.flag)
===============================================================================

PURPOSE:
- Essential for CI/CD automation
- Reliable environment readiness detection
- Prevents race conditions in startup sequences
- Enables automated testing integration

FLAG CONTENT EXAMPLE:
```json
{
  "timestamp": 1725283920000,
  "sessionId": "startup-1725283920000-abc123",
  "readyServices": [
    "postgres", "redis", "ollama-primary", 
    "gpu-embedding-service", "enhanced-rag", "sveltekit"
  ],
  "startupDuration": 45230,
  "environment": "development"
}
```

FLAG LIFECYCLE:
1. 🔄 STARTING    - Services initializing, no flag
2. ⏳ MONITORING  - Health checks running, flag pending  
3. ✅ READY       - All critical services up, flag created
4. 🛑 SHUTDOWN    - Flag removed on graceful shutdown
5. ⚠️ EXPIRED     - Flag auto-expires after 30 minutes

AUTOMATION USAGE:
```bash
# Wait for system ready (perfect for CI/CD)
while [ ! -f "logs/ready.flag" ]; do 
  echo "Waiting for system ready..."
  sleep 2
done
echo "✅ System ready for testing!"

# Or use automation script
node scripts/startup-automation.mjs wait && npm run test:e2e
```

SERVICE CATEGORIES:
```
CRITICAL SERVICES (must be ready):

├── redis (6379)              - Caching & queuing  
├── ollama-primary (11434)    - AI model serving
├── gpu-embedding-service     - Vector embeddings
├── enhanced-rag (8094)       - RAG AI service
└── sveltekit (5173)          - Frontend application

OPTIONAL SERVICES (retry with backoff):
├── upload-service (8093)     - File processing
├── neo4j (7474)              - Graph database
├── qdrant (6333)             - Vector storage
└── minio (9000)              - Object storage
```

HEALTH GRADES:
- 🟢 EXCELLENT (<50ms)   - Optimal performance
- 🟡 GOOD (<200ms)       - Acceptable performance  
- 🟠 FAIR (<1000ms)      - Degraded performance
- 🔴 POOR (>1000ms)      - Poor performance
- ❌ CRITICAL (down)     - Service unavailable

DEPENDENCY TRACKING:
Services wait for their dependencies before attempting startup:
- enhanced-rag depends on: postgres, ollama-primary
- upload-service depends on: postgres, redis
- sveltekit depends on: enhanced-rag, gpu-embedding-service

===============================================================================
🔄 RETRY LOGIC & RESILIENCE
===============================================================================

RETRY STRATEGY:
- Exponential backoff: 5s → 10s → 20s delays
- Max 3 attempts per optional service
- Critical services block until ready
- Race condition protection for slow dependencies

RETRY FLOW:
```
Service Start → Health Check → Ready? → ✅ Continue
     ↓               ↓           ↓
Failed Service → Retry Count++ → Max Retries? → ❌ Mark Failed
     ↓               ↓              ↓
Backoff Delay → Exponential → Wait → Retry Health Check
```

FAILURE HANDLING:
- Critical service failure = BLOCK startup
- Optional service failure = LOG warning, continue
- Dependency failure = DEFER dependent services
- Timeout = FAIL with detailed error context

📈 PERFORMANCE DIFF & REGRESSION DETECTION
===============================================================================

DIFF TRACKING FEATURES:
- Startup time comparisons (current vs previous)
- Service status change detection
- Retry count monitoring
- Health grade degradation alerts
- New/removed service detection

REGRESSION ALERTS:
```
🔴 CRITICAL: Critical service failed (was ready)
🟠 HIGH:     Startup time increased >5 seconds  
🟡 MEDIUM:   Optional service retry count increased
🟢 LOW:      Minor performance variations
```


🔍 DEBUGGING & TROUBLESHOOTING
===============================================================================

COMMON ISSUES & SOLUTIONS:

❌ Ready flag never appears:
→ Check logs/startup-summary.json for failed critical services
→ Verify postgres/redis are running and accessible
→ Check Ollama model availability

⚠️ High startup times:
→ Review logs/startup-diff.json for regression analysis
→ Check system resource usage during startup
→ Verify dependency service health

🔄 Services stuck in retry loops:
→ Check service logs for specific error details
→ Verify network connectivity and port availability
→ Review dependency chain for circular issues

📊 Missing telemetry data:
→ Verify /api/v1/telemetry/upload endpoint is accessible
→ Check uploadTelemetry service initialization
→ Review console logs for telemetry emission

DIAGNOSTIC COMMANDS:
```bash
# Full system status
curl -s "http://localhost:5173/api/v1/startup?action=health" | jq

# Check ready flag directly
cat logs/ready.flag | jq

# View recent telemetry
curl -s "http://localhost:5173/api/v1/telemetry/upload" | jq
```
