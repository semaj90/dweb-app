## 🏗️ **ENHANCED ARCHITECTURE WITH RABBITMQ MESSAGE QUEUE**

### **3. AI Processing: Concurrency & Embeddings 🧠**
This is where the heavy lifting happens, designed not to block the user.

**Go-routines (Concurrency)**: On a cache miss, the main API handler does not perform the summarization itself. Instead, it spins up a go-routine (a lightweight thread) to handle the task in the background. The API can then instantly respond to the frontend with a "Job Started" status. The frontend can poll another endpoint to check for the result.

**Langchain.js / Llama.cpp / Legal-BERT**: The background go-routine uses a library like Langchain to orchestrate the summarization. It feeds the text to your local Llama.cpp instance, which runs the specialized Legal-BERT model to generate a high-quality summary.

**Vector Embeddings (Nomic-embed & PostgreSQL/pg_vector)**: After generating the summary, the worker also generates a vector embedding of the original document using the nomic-embed-text model. This vector (a list of numbers representing the document's meaning) is then stored in your PostgreSQL database alongside the document using the pg_vector extension. This doesn't help with the immediate summary but is crucial for future features like semantic search ("find similar documents").

### **4. RabbitMQ Message Queue - Scalable RAG Ingestion Pipeline 🐰**

**RabbitMQ Integration**: Acts as the "central post office" for decoupling data sources from complex processing and storage steps, enabling resilient, asynchronous backend operations.

#### **RAG Ingestion Workflow:**

**1. The Producer: Document Ingestion 📮**
```typescript
// Initial service publishes to RabbitMQ exchange
const documentMessage = {
  "document_id": "xyz",
  "source_location": "s3://bucket/legal-doc.pdf",
  "content": extractedText,
  "metadata": {
    "case_id": "case-123",
    "document_type": "brief",
    "priority": "high"
  }
};

// Publish to 'docs-to-process' queue
await rabbitMQ.publish('legal-exchange', 'docs.new', documentMessage);
```

**2. The Chunker Consumer: Text Segmentation ⚙️**
```typescript
// Middleware service subscribes to 'docs-to-process'
rabbitMQ.consume('docs-to-process', async (message) => {
  const doc = JSON.parse(message.content);
  const chunks = chunkDocument(doc.content, 512, 50); // 512 tokens, 50 overlap
  
  chunks.forEach((chunk, index) => {
    const chunkMessage = {
      "document_id": doc.document_id,
      "chunk_id": index,
      "text": chunk,
      "metadata": doc.metadata
    };
    
    // Publish to 'chunks-to-embed' queue
    rabbitMQ.publish('legal-exchange', 'chunks.new', chunkMessage);
  });
});
```

**3. The Embedder Consumer: Vector Generation 🧠**
```typescript
// Embedding service processes chunks
rabbitMQ.consume('chunks-to-embed', async (message) => {
  const chunk = JSON.parse(message.content);
  
  // Generate embedding using nomic-embed-text
  const embedding = await nomicEmbedding.embed(chunk.text);
  
  const vectorMessage = {
    "chunk_id": chunk.chunk_id,
    "document_id": chunk.document_id,
    "text": chunk.text,
    "vector": embedding, // 384-dimensional array
    "metadata": chunk.metadata
  };
  
  // Publish to 'chunks-to-store' queue
  rabbitMQ.publish('legal-exchange', 'vectors.ready', vectorMessage);
});
```

**4. The Neo4j Loader Consumer: Knowledge Graph Storage 🕸️**
```typescript
// Final service loads into Neo4j
rabbitMQ.consume('chunks-to-store', async (message) => {
  const vector = JSON.parse(message.content);
  
  // Create Neo4j nodes and relationships
  await neo4j.run(`
    MERGE (doc:Document {id: $docId})
    CREATE (chunk:Chunk {
      id: $chunkId,
      text: $text,
      embedding: $vector
    })
    CREATE (chunk)-[:BELONGS_TO]->(doc)
    CREATE (doc)-[:HAS_CHUNK]->(chunk)
  `, {
    docId: vector.document_id,
    chunkId: vector.chunk_id,
    text: vector.text,
    vector: vector.vector
  });
  
  // Also store in PostgreSQL for vector similarity search
  await pgVector.storeEmbedding(vector);
});
```

### **5. Offline & Background Sync (Service Workers) 🌐**
Service Workers are the final piece that makes your application incredibly robust.

**Offline Queuing**: A Service Worker can intercept outgoing API requests. If the user is offline and triggers a summarization, the service worker can save that request and automatically send it when the connection is restored.

**Background Sync**: The service worker is also perfect for synchronizing the drafts saved in Loki.js/IndexedDB with your main PostgreSQL database in the background, ensuring that offline work is never lost.

#### **Key RabbitMQ Architecture Advantages:**

**Decoupling**: The document ingestion service knows nothing about chunking, embedding, or Neo4j. It just drops a message and moves on.

**Scalability**: If embedding is your bottleneck, you can run multiple instances of the Embedder service. RabbitMQ automatically distributes workload among them.

**Resilience**: If Neo4j is temporarily down, messages pile up in the chunks-to-store queue. Once the database is back online, the loader service resumes processing exactly where it left off.

**Message Routing**: Different document types can be routed to specialized processing queues (e.g., `legal.contracts`, `legal.evidence`, `legal.briefs`).

## 📊 **COMPLETE TECHNICAL ARCHITECTURE FLOW**

```
User Types → Debounced Handler (500ms) → Local Auto-save (Loki.js/IndexedDB)
                    ↓
            SHA-256 Hash → Go Microservice API → Redis Cache Check
                    ↓
            Cache Hit (Instant) OR Cache Miss → Background Go-routine
                    ↓
            RabbitMQ Publisher → Document Queue → Chunker Consumer
                    ↓
            Chunks Queue → Embedder Consumer → Vectors Queue
                    ↓
            Neo4j Loader → Knowledge Graph + PostgreSQL/pg_vector
                    ↓
            Job Polling → Frontend Update → Cache Result
```

This architecture effectively separates concerns, providing a snappy user experience on the frontend while using powerful concurrent patterns on the backend to handle slow, intensive AI tasks without interruption. The RabbitMQ message queue ensures scalable, resilient RAG ingestion that can handle enterprise-grade document processing workloads.
